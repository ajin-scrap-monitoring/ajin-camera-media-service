# 날짜 녹화 누락 개선 회신 — 2026-11-06

전달용 회신이다. 실제 메신저·이메일 전송은 하지 않았다. 아래는 수정본의 실제 적용·검증 결과다.

## 원인과 수정

날짜 녹화가 현재 시각보다30초 이상 뒤처지면 버퍼 JPEG가 있어도 지난 구간을 건너뛰던 동작을 확인했다. 버퍼 정리도 날짜 미처리 커서를 보호하지 않았다. 입력 수신이 정상이어도 저장 영상이 빠지는 직접 원인이었다.

지연에는 여러 비용이 함께 작용했다. 큰 날짜 JSON을 반복 저장하는 커밋, 보관된 과거 조각까지 다시 집계하는 공간 조회, 전체 coverage 재계산을 줄였다. 운영에서 인코딩 최대1.22초에 비해 DB 커밋 최대12.76초·공용 잠금 최대14.47초가 관측됐다. SD 불량이나 인코딩만을 원인으로 단정하지 않았다.

FULL 커밋을 유지한 별도 파일 시험에서는 자동 checkpoint 적용160회 커밋의 최대 시간이9.837초, 자동 checkpoint 해제 시0.042초였다. 후자의 별도 checkpoint 자체는12.555초였다. 실제 저장 장치 지연이 남으므로 DB 처리 개선과 순간 적체 흡수를 함께 적용했다.

- 버퍼에 남은 JPEG를 오래된 구간부터 처리하며30초 지연만으로 버리지 않는다. 한 tick당 최대3개 슬롯을 처리한다. 실제 프레임이 없는 과거 구간만 빠르게 건너뛴다.
- 날짜 미처리 커서 이후 JPEG를 시간·용량 정리에서 보호한다. 재시작으로 중단된 미완료 인코딩도 원본이 있으면 재처리한다. 기존 완료 조각과 과거 누락 기록은 보존한다.
- 날짜 JSON 변경분·작은 상태 요약·증분 coverage를 사용한다. 과거 수정·삭제·날짜 경계에서는 전체 계산으로 돌아가며 공개 응답은 같은 필드로 제공한다.
- 프레임과 정리 커밋의 FULL 내구성은 유지한다. checkpoint는 별도 연결의 PASSIVE 작업으로 분리한다. 일반 만료 정리는 최대64개씩 나누고 실제 용량 압박에서는 필요한 만큼 정리한다.
- 저장 전 RAM 큐를100프레임에서 전체1,200프레임·96MiB 이중 한도로 변경한다. 30fps에서 프레임 한도는 약40초이나 큰 JPEG는 바이트 한도에 먼저 도달한다. 저장 작업이 큐 밖에서 가진 최대10프레임은 별도다. 실시간 조회 큐는 그대로다.
- 정상 종료 시 접수된 큐가 저장될 때까지 기다린다. 저장 작업이 비정상 종료되면 남은 손실을 기록하고 자원을 정리한 뒤 오류를 보고한다. 전원 장애·SIGKILL·종료 유예 초과 시 RAM 프레임까지 보존하는 기능은 아니다.
- 내부 진단에 단계별 시간, 녹화 지연, 수신 큐 프레임·바이트, 실제 손실 원인을 남긴다. 공개 API의 경로·JSON 필드·누락 reason_code는 유지한다.

## 백엔드 측 확인 범위와 제한

기존 조회·삭제·이벤트·다운로드 계약을 그대로 사용하면 된다. RAM 큐 한도나 내부 DB 변경은 백엔드 계약에 추가되지 않는다. 실제 백엔드 컨테이너에서 미디어 주소를 직접 호출하는 검증과 백엔드 중개·인증 게이트웨이·대시보드의 전체 통합 검증은 구분한다.

저장 용량이 부족하거나 입력 자체가 없으면 누락이 생길 수 있으며 원인을 기록한다. 이미 원본이 사라진 과거 시간은 복구하지 못한다. 짧은 운영 시험은24시간 무누락 보장이 아니다. 날짜 전환·보관 작업은 자동 회귀 시험을 포함하며 실제 시간 자정을 통과한 장기 검증은 별도다.

변경분을 모르는 예전 이미지로 복귀할 때는 서비스를 중지하고 현재 코드의 `DailyCatalog.materialize_snapshots()`를 같은 저장소에서 한 트랜잭션으로 실행한 뒤 예전 이미지를 시작한다. 과거 DB 백업을 덮어쓰지 않는다. 상세 절차는 README를 따른다.
