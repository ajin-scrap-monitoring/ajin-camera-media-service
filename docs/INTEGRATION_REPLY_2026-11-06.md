# 날짜 녹화 누락 개선 회신 — 2026-11-06

전달용 초안이며 실제 메신저·이메일 전송은 하지 않았다. 실행 버전·배포 결과·관찰 수치는 검증 완료 후 아래에 추가한다.

## 확인한 문제

11/03~11/05 날짜 확보 길이와 gap_count가 요청서와 일치했다. 11/05 재생 길이53681초, gap_count187891, 재생 길이와 벽시계 구간 합 차이192.108초를 확인했다. 요청서의11/06 06:39:20~06:40:20 KST 구간도 저장 조각 재생 길이 합49.133초로 재확인했다.

11/06 12시대에는 버퍼 JPEG가 남은26초 구간에468장이 있으면서 완료 날짜 조각은0개인 사례를 확인했다. 기존 구현은 현재 시각과 날짜 처리 cursor 차이가30초를 넘으면 JPEG 존재를 확인하지 않고 건너뛰었다. 버퍼의 시간·바이트 정리도 날짜 미처리 cursor를 보호하지 않았다.

60초 계측에서는 JPEG 약85.9MB 대비 미디어 Python 쓰기 요청471.6MB, 확보 길이 증가16.134초, CPU 평균0.735코어/한도2코어를 관측했다. SD 쓰기 대기가 있었고 날짜 메타데이터는 약9.55MB였다. 큰 날짜 JSON의 반복 저장과 공용 잠금·저장 대기가 적체를 증폭시키는 근거다. 단독 하드웨어 원인으로 확정하지 않는다.

운영 부하 중 별도64MiB 파일 시험에서 SD/서버 SATA SSD 순차 쓰기40.4/45.4MiB/s, 4KiB 쓰기+fsync 평균17.2/27.6ms, 최대3610.3/66.5ms였다. 짧은 단일 관측이며 순차 대역폭만으로 누락 원인이나 SSD 이전 효과를 확정하지 않는다. 운영 원본을 시험 파일로 사용하지 않았고 시험 파일은 정리했다.

## 수정 내용

- 30초 지연만으로 실제 저장된 JPEG를 건너뛰지 않는다. 같은 카메라의 오래된 구간부터 처리하고 한 tick당 최대3개 슬롯으로 작업을 제한한다.30초 설정은 지연 관측·확실히 빈 과거 구간을 빠르게 넘어가는 기준으로 유지한다.
- 날짜 cursor 이후의 미처리 프레임을 시간·바이트 정리에서 보호한다. 기존2GiB 버퍼와 전체/날짜 예산은 유지한다. 보호된 프레임으로 버퍼가 가득 차면 새 입력 저장을 명시적으로 거절하므로 무제한 적재나 무손실을 보장하지 않는다.
- 재시작 시 이미 내구 저장된 JPEG 범위까지 SERVICE_INTERRUPTED로 덮어 제외하지 않는다. 인코더가 중단됐더라도 원본 JPEG가 있으면 다시 처리한다. 완료돼 있던 조각은 재인코딩하지 않는다.
- 조각 완료의 revision 증가는 작은 별도 행에 원자적으로 저장한다. 완료 때마다 큰 날짜 JSON 전체를 다시 저장하지 않는다. 기존 get/list 응답의 revision은 같은 필드로 제공하며, 재시작과 구버전 rollback 이후 값을 유지한다.
- 완료 슬롯 경계에서 기존 coverage·gaps·available_intervals 스냅샷을 저장한다. 할 일이 없는 tick에서는 큰 날짜 JSON을 반복 조회하지 않는다. 원본 촬영 시각이나 누락 없는24시간을 만들어내지 않는다.
- 프레임/정리의 FULL 내구성 커밋은 종료까지 기다리는 worker에서 수행한다. 취소가 커밋 완료와 겹쳐도 실제 저장된 JPEG를 지우지 않는다.
- 내부 로그에 단계별 누적/최대 시간과 원인별 건수를 제한된 크기로 기록한다. catalog_lock_wait/hold, catalog_commit, prune_commit, frame_store, daily_encode, coverage_refresh, space_check, backlog_seconds, ingest_queue_frames를 측정한다.

## 계약 호환과 진단

기존 API 경로·JSON 필드·공개 reason_code·시간 단위는 유지한다. 새 오류 필드나 새 gap reason을 백엔드에 일방적으로 추가하지 않는다. 기존 BUFFER_DROPPED 과거 기록은 그대로이며, 새 내부 카운터 ingest_queue_full·source_frames_missing·backlog_frames_preserved·interrupted_segment_buffered로 원인을 구분한다. 공개 UNKNOWN_CAPTURE_LOSS는 실제 확보 구간 밖에서 별도 입증 사유가 없는 경우의 기존 의미를 유지한다.

STORAGE_FULL/INSUFFICIENT_STORAGE는 내부 진단에서 daily_budget·total_budget·minimum_free·buffer_capacity를 구분한다. 예산을 늘리거나 물리 여유만 보고 실패를 무시하지 않는다. 실제 인코딩·저장 실패의 기존 오류 의미는 유지한다. 과거에 이미 누락 확정된 시간을 자동 복구·재분류하지 않는다. 재시작 중인 미완료 작업의 남은 입력만 보호한다.
