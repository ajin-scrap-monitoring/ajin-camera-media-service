# 2026-11-03 카메라 미디어 후속 계약

LC-1·LC-2·LC-3·LC-4·LC-6의 카메라 미디어 담당 범위다. LC-5 라이다 배치·좌표·설정 버전의 일관성 확인은 오케스트레이션/라이다 측에서 처리한다. 기존 JSON 필드·상태·API 경로를 유지한다. 실제 운영 적용 버전과 측정 결과는 VALIDATION.md를 따른다.

## 저장 장치와 이전

컨테이너 내부 루트는 `/var/lib/camera-media`를 유지한다. SD 전용 호스트 경로는 `/srv/ajin-camera-storage/sd/camera-media`이며, 기존 `/srv/scrap-monitoring/media` SD 마운트는 유지한다. JPEG 버퍼, 날짜 TS·MP4, 이벤트 MP4, HLS 임시 파일, SQLite와 파일 정보 저장소가 같은 루트에 있다.

SD UUID와 실제 커널 장치·ext4·쓰기 권한·마운트 ID를 시작 전에 검사한다. 실행 중에도 쓰기/파일 접근을 보호하고, 호스트 마운트의 단절을 전파하는 별도 읽기 전용 witness를 확인한다. 잘못된 장치·분리·읽기 전용·마운트 변경은 저장 실패로 처리하며 SSD 디렉터리를 대신 만들지 않는다. 실패 후에는 올바른 마운트를 복구하고 서비스를 재시작한다. 영상 수신 상태의 `accepted_jpeg_receipt` 의미는 바꾸지 않는다. 영상 수신 healthy는 녹화 저장 성공을 뜻하지 않으며 저장 실패는 서비스 건강 검사와 녹화 오류·누락에 반영된다.

기존 SSD 원본을 이동/삭제하지 않고 복사한다. 최종 복사·검증은 미디어 서비스만 중지한 상태에서 수행한다. 모든 파일의 해시·크기·mtime·권한·소유자·상대 경로와 SQLite/WAL/SHM·테이블 개수를 비교한다. 검증 중 원본 DB에 서비스를 실행하거나 새 데이터 위에 이전 DB를 덮어쓰지 않는다. SD에서 새 녹화를 시작한 뒤 SSD로 복구하려면 새 데이터와 카탈로그를 먼저 조정해야 한다. 절차와 도구는 [SD_STORAGE.md](SD_STORAGE.md) 참조.

## 용량과 보관

현재 운영은 `ajin-camera-media-service:8d5d584`이며 전체48GiB·날짜42GiB·작업 공간10GiB·최소 여유5GiB·JPEG2GiB·활성 클립32개입니다. 기존 이벤트 전후30초/보관30일과 날짜 보관30일을 유지했습니다. 이는 현재 적용값이며 새 보관 기간 합의가 아닙니다.

추가 환경 설정:

| 설정 | 의미 |
|---|---|
| `MAX_MEDIA_STORAGE_BYTES` | 전체 루트의 파일·DB/WAL·버퍼·클립·날짜 영상·임시 파일을 포함하는 애플리케이션 예산. 미설정/0이면 기존 종류별 제한만 적용 |
| `MAX_DAILY_STORAGE_BYTES` | 날짜 TS·MP4·HLS 임시 파일과 미완료 작업 예약을 합산하는 날짜 영상 예산 |
| `DAILY_ARCHIVE_WORKSPACE_BYTES` | 새 상시 녹화가 남겨 둘 MP4 준비 공간의 하한. 실제 미보관 날짜 출력 예상량이 더 크면 그 값을 사용. 0은 기존 동작 |
| `MIN_FREE_STORAGE_BYTES` | 실제 파일시스템에 남기는 여유 공간 |
| `MAX_BUFFER_BYTES` | JPEG 버퍼 상한 |
| `MAX_CLIP_JOBS` | collecting/processing 클립 개수 한도 |

출력으로 이미 센 바이트는 동일 stat 관측을 기준으로 예약에서 차감한다. 출력 생성이 끝나면 추가 쓰기 예약을 해제하고 실제 출력 크기를 검사한 후 ready로 공개한다. 새로 생성한 파일이 예산을 넘으면 실패 처리·정리하며 원본 영상은 유지한다. 중단된 처리 파일을 재시작 후 복구할 때도 실제 예산을 검사한다. JPEG 저장도 전체 예산을 검사하며 예약 변경 시 용량 스냅샷을 무효화한다.

이는 파일 생성 접수·완료를 제어하는 애플리케이션 예산이다. FFmpeg가 추정치보다 큰 임시 파일을 쓴 순간의 사용량까지 커널에서 차단하는 파일시스템 하드 쿼터는 아니다. 실제 공간 부족·쓰기 실패는 오류로 유지한다. 상한에 도달했다고 미만료된 오래된 영상을 임의로 지우지 않는다. 보관 나이와 용량 중 먼저 제약되는 조건에 따라 신규 녹화/추출이 거부될 수 있다. 약64GB SD에 하루 약7GB 영상30일 보관을 보장하지 않는다.

| 종류 | 보관 시작·정리 규칙 | 원본과의 관계 |
|---|---|---|
| JPEG 버퍼 | 수신 시각 기준300초가 지난 파일을 정리. 용량 부족 시 더 이른 정리 가능. 진행 작업 pin은 유지하며 전부 pin이면 새 저장 실패 | 상시 TS/완료 클립과 별개. 버퍼는 최대2GiB 등 운영 설정 적용 |
| 날짜 TS | 날짜 보관 기한까지 유지하거나, 해당 날짜 MP4의 전체 안전 검증·매핑 완료 후 중복 TS 정리 | MP4 검증 전에는 원본 삭제 안 함. 진행 추출 pin 해제까지 정리 보류 |
| 날짜 MP4 | 한국 날짜 종료 시각 + 그 날짜에 저장된 `retention_days`. 날짜 `expires_at`와 `export_expires_at`은 같은 보관 끝 | 전체 다운로드는 준비된 MP4 전송. 다운로드를 눌러 새 인코딩하지 않음 |
| 이벤트/요청 구간 MP4 | 접수 시 정책을 저장하고 실제 완료 시각 + 저장한 `retention_days` | 완료 후 독립 보관. 원본 날짜 만료가 완료 클립을 삭제하지 않으며, 클립 삭제도 원본을 삭제하지 않음 |
| HLS 임시 TS | 보관 MP4에서 스트림 복사한 재생 캐시. 기본64MiB/60초, 동시 실행2/작업8. 접근·유지보수 시 만료/용량 정리 | 삭제해도 보관 원본 유지. 다음 요청에서 다시 준비할 수 있음 |

**다운로드 완료·중단·Range·재다운로드는 파일 삭제나 보관 연장을 유발하지 않는다.** 유효한 ready 파일은 반복 재사용한다. 미디어 `expires_at`은 UTC 접근 기한이며 물리 파일 정리 완료 시각이 아니다. 백엔드가 전달하는 `expiresAt`도 해당 의미로 매핑한다.

JPEG와 클립 만료 정리는 저장 작업 및 약5초 주기의 관리 작업이 실행한다. 날짜 만료·정리 재시도도 약5초 주기이며 진행 pin/I/O 실패에 따라 늦어질 수 있다. 날짜의 `cleanup_state`·`cleanup_completed_at`·`cleanup_error`를 그대로 사용하고 `space_reclaimed=null`을 유지한다. 열린 파일 핸들의 블록 회수까지 단정하지 않는다. 이벤트 파일은 접근 차단410과 물리 삭제 완료를 같은 것으로 표시하지 않는다.

## 파일 정보 영구 저장

기존 두 media-info API와 JSON 계약을 유지한다.

```http
GET /api/v1/clips/{clip_id}/media-info
GET /api/v2/daily-recordings/{recording_id}/media-info
```

- 생성·전체 검증으로 실제 측정한 codec/width/height/분수 명목fps/size_bytes를 영구 저장한다. 설정값을 측정값으로 대체하지 않는다.
- 유효한 저장값이 있으면 FFmpeg를 실행하지 않는다. 서비스 재시작·메모리 캐시128개 초과도 같은 규칙이다.
- 장치·inode·크기·mtime·ctime의 내부 식별 근거로 교체를 확인하고 검사 전후 변화를 검증한다. 내부 경로·식별값은 공개 JSON에 넣지 않는다.
- 과거 미측정/무효 기록은 요청 시 제한된 검사로 보완한다. 같은 파일은 singleflight, 실행2/접수8 한도다. 실패는 unknown으로 남기고 이후 요청에서 재시도한다. 시작 시 전수 검사는 하지 않는다.
- 파일 정보 저장 실패 때문에 정상 영상의 ready·재생·보관 상태를 취소하지 않는다. 영상 카탈로그 트랜잭션과 선택적인 정보 저장을 분리한다.
- 날짜 `file`과 `segments`는 각각 MP4 파일과 원본 조각 측정 범위다. 일부 조각만 확인되면 partial/unknown 및 `measured`·`total`·`mixed=null`을 유지한다. TS 정리 후 집계는 검증된 같은 MP4에 연결된 근거가 있을 때만 사용한다. 교체되거나 근거 없는 과거 MP4는 원본 집계를 임의로 ready로 만들지 않는다.
- 삭제·만료·등록 카메라 검증과410/404는 저장값 조회에서도 유지한다. `source=file_probe`와 unknown/null 규칙은 바꾸지 않는다.

## 녹화·재생

조각 경계를 가로지르는 실제 앞뒤 수신 프레임이1초 이내로 이어지고 명시적 손실이 없는 경우에만 이미 수신한 프레임의 표시 구간을 경계까지 유지한다. 단순히 마지막 프레임을 늘려 실제 누락을 숨기지 않는다. 알려진 짧은 손실과1초가 넘는 실제 입력 공백은 유지한다. 새로 계산하는 coverage는 짧은 미확보 구간도 숨기거나 가용 구간에 붙이지 않는다. 기존 종료 날짜에 저장된 과거 집계를 무손실로 다시 썼다고 보고하지 않는다.

파일 open/stat/seek/read/close, HLS 조각 준비·캐시 스캔, 큰 JSON·playlist·coverage 계산을 공용 이벤트 루프에서 분리한다. 취소된 요청은 작업 스레드와 FFmpeg가 끝나기 전에 파일 소유권·원본 pin·예약을 해제하지 않는다.

측정 도구는 `tools/media_delivery_probe.py`다. 완성 JPEG 사이 간격, 동일 조각의 첫/반복 요청, playlist 크기, 관찰 구간에 새로 완성된 조각의 경계를 구분한다. 수신과 전송의 공백이 함께 나타나도 원본 생성 시각 없이 시뮬레이터 내부 원인을 확정하지 않는다. 운영 전후 수치와 기간·캐시 조건은 VALIDATION.md에 기록한다.

## LC-6 지원과 오류

선택 썸네일은 기존 `unsupported`/null이다. 원본 프레임 생성 시각은 현재 JPEG/WSS 입력에 없으므로 `capture_timestamp_supported=false`, nullable 시각, `time_basis=server_received_at`을 유지한다. 라이다와 시뮬레이터 생성 시각을 공유한다고 주장하지 않는다. 새 썸네일·생성 시각 필드/상태를 사용하려면 별도 계약이 필요하다.

`EXPORT_CAPACITY_EXCEEDED`는 현재 미디어에서 발생시키지 않는다. 동시/대기 한도는 아래 기존 오류로 구분한다.

| 상황 | HTTP / code | 재시도 |
|---|---|---|
| 활성 클립 한도 | 503 `SERVICE_BUSY` | 진행 작업 종료 후 같은 식별자로 재요청. 신규 접수 전 실패는 파일을 만들지 않음 |
| 날짜/전체 예산·디스크 여유 부족 | 503 `INSUFFICIENT_STORAGE` | 공간·정책 문제 해소 후 재시도. 요청별 failed 클립은 기존 계약의 `retry_failed=true` 사용 |
| 파일 정보 접수8개 초과 | 503 `METADATA_CAPACITY_EXCEEDED` | 진행 검사 종료 후 조회 재시도 |
| HLS 준비 작업8개 초과 | 503 `PLAYBACK_CAPACITY_EXCEEDED` | 진행 준비 종료 후 같은 조각 요청 |
| SD 마운트/장치·권한·I/O 오류 | 503 `STORAGE_UNAVAILABLE` 등 기존 저장 경로 오류 | 원인 복구, 마운트 실패 latch는 서비스 재시작 필요 |

```json
{"error":{"code":"SERVICE_BUSY","message":"Too many active recordings."}}
```

ready/processing 파일 재사용과 중복 키 규칙은 그대로다. `Retry-After` 고정 보장은 없으며 백엔드는 동시 재시도 폭주를 피하고 상태 조회를 이용한다. 새 오류 문자열을 임의로 기존 오류의 별칭으로 추가하지 않았다.
