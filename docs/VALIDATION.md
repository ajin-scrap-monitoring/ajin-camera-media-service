- 생성 MP4의 H.264 디코딩, 해상도, fast-start 배치와 프레임 시간 간격 유지.
- MJPEG 응답의 JPEG 원본 바이트, multipart 헤더, 사용 가능한 영상 없음 처리.
- 클립 목록 페이지네이션 및 잘못된 커서, HTTP Range·다운로드.

- 바이트 한도, 활성 이벤트 프레임 보호, 잘못된 JPEG의 인코딩 실패.
- 부분 파일 쓰기 실패의 잔여 파일 정리, 일시적 SQLite 결과 저장 오류의 재시도.

인코딩 테스트는 개발 의존성 imageio-ffmpeg의 실행 파일과 Pillow로 만든 JPEG를 사용한다. 테스트에서 FFmpeg를 모의 처리하지 않고 실제 파일 생성·디코딩을 검사한다. 저장소 장애 복구 등 특정 오류 테스트만 해당 경계에 장애를 주입한다.

### 실제 시간으로 진행한120초 합성 부하

독립 컨테이너 `ajin-camera-media-daily-validation`에 JPEG를 전송했다. 원본1920×1080, 목표30fps, 실제 전송3,550프레임/120초=29.58fps(의도적1.5초 단절 포함), JPEG164,768,997바이트. MJPEG 조회161,158,219바이트와 전후3초 이벤트 MP4 생성이 함께 성공했다. 재연결2회, 이벤트 ready, 날짜 error=null. 해당 시험 중 추가 저장 길이 약118.367초였다.

CPU24표본 평균50.94%/최대204.64%(100%=1코어, 제한2코어), 메모리 표본 최대531.5MiB/제한3GiB. 단순 움직이는 도형 합성 영상의 TS 저장량은 초기 표본 약3.3GiB/day 환산이었다. 이 값은 실제 스크랩 영상의 용량 추정에 사용하지 않는다. 다중 카메라·실제 장비·24시간 처리량 보장이 아니다.

첫 동시 시험에서는 테스트 클라이언트가 첫 JPEG 전 MJPEG503을 재시도하지 않아 최종 실패했다. 도구를 보완한 두 번째 시험은 종료 코드0/`state=passed`로 기록했다. 첫 실행은 서버 자동 시험과 겹쳐 BUFFER_DROPPED 누락이 있었으며 누락을 숨기지 않고 카탈로그에 남겼다. 브라우저의 초기 조각 로드 timeout은 비치명적 오류로 재시도 후 재생됐고 일부 표시 프레임 drop이 관찰됐다. 상대 대시보드의 플레이어를 통과한 시험으로 보고하지 않는다.

### Linux 개발 번들과 운영 실행 파일

Linux 개발용 imageio-ffmpeg7.0.2는 유효 TS 읽기에서 종료 코드-11로 충돌했다. 같은 파일이 운영 `/usr/bin/ffmpeg`7.1.3에서 정상 디코딩됨을 확인했다. 서버 자동 시험에 `IMAGEIO_FFMPEG_EXE=/usr/bin/ffmpeg`를 설정하여 실제 운영 조합으로 전체 검증했다. Windows 시험은 번들7.1.0을 사용했다.
